💰 Open Wealth — Tutorial da Fase 4

Da API em arquivo local a um ambiente containerizado com Postgres, coleta diária automática e os primeiros endpoints de leitura — a base do dashboard.

1. O que a Fase 4 entrega

  1. Dockerização — app + banco open-wealth-db (Postgres) em docker-compose, substituindo o SQLite local.
  2. Scheduler diário — o snapshot passou de manual (POST /sync) a automático, coletando todo dia [CONFIRMAR: horário/cron].
  3. Endpoints de leitura — GET /carteira e GET /historico/evolucao expõem o patrimônio consolidado e a série temporal.
  4. Views SQL — v_alocacao_classe e v_alocacao_instituicao agregam no banco, não na aplicação.

3. Dockerização — do SQLite ao Postgres

A troca de banco foi o maior risco técnico da fase: o repositório era escrito contra SQLite. A saída foi trocar a implementação sem trocar o contrato — os testes da Fase 1 continuaram verdes, agora contra Postgres de verdade.

docker-compose — os serviços

ServiçoPapel
open-wealth-dbPostgres com volume persistente
open-wealth-appFastAPI + scheduler no mesmo container [CONFIRMAR]

Verificação direta no banco (sem passar pela API):

# acessar o Postgres dentro do container
docker exec -it open-wealth-db psql -U openwealth -d openwealth
⚠️ Lição do SQLite que carregamos: reiniciar o server após recriar o banco. Com Docker, o equivalente é docker compose down -v para destruir o volume — senão dados fantasmas sobrevivem à "recriação".

4. Scheduler diário — o histórico começa a se formar sozinho

Na Fase 2 o sync dependia de um curl manual. Agora o scheduler dispara todo dia, o que significa que o histórico de snapshots cresce sem ninguém olhar. Como a dedup por dia vive no repositório (Fase 2), rodar duas vezes ou reiniciar o container não infla o histórico.

Por que isso importa para a Fase 5

Os indicadores de rentabilidade (30d, YTD) precisam de série temporal. É a coleta diária automática desta fase que constrói, silenciosamente, a matéria-prima dos gráficos de amanhã.

7. Validação de ponta a ponta (o que provou que funciona)

Com dados reais sincronizados do Pluggy, a verificação final foi feita direto no Postgres e via API:

# o histórico tem datas distintas e totaliza corretamente?
docker exec -it open-wealth-db psql -U openwealth -d openwealth -c \
  "SELECT snapshot_date, COUNT(*), SUM(amount) FROM snapshots
   GROUP BY snapshot_date ORDER BY snapshot_date;"

# a view agrega sem tocar em Python?
docker exec -it open-wealth-db psql -U openwealth -d openwealth -c \
  "SELECT * FROM v_alocacao_classe ORDER BY snapshot_date DESC LIMIT 5;"

# a API expõe o que o banco tem?
curl http://localhost:8000/api/v1/carteira
curl http://localhost:8000/api/v1/historico/evolucao

Resultado: patrimônio consolidado de R$ 42.695,23 em snapshot do dia, consistente entre banco, views e API.

💡 Detalhe que apareceu no caminho: o Postgres com NUMERIC(20,4) retorna Decimal (SQLite retornaria float). Se algum código comparava valores com == 0.0, isso quebra silenciosamente. Foi corrigido durante a fase.
