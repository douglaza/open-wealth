1. Ponte Contextual: O que foi construído nas Fases 3, 5 e 6

Antes de entendermos como garantimos a qualidade do código na Fase 7, vale recapitular a evolução do Open Wealth nas fases intermediárias (3, 5 e 6), que transformaram o script de consolidação em um ecossistema patrimonial completo:

📈 Fase 3: Histórico Patrimonial & PostgreSQL

Objetivo: Sair da foto pontual de "hoje" e criar uma linha do tempo confiável do patrimônio.

  • Snapshots diários: Gravação idempotente por instituição e data via SnapshotRepository. Se o sync rodar 10 vezes no mesmo dia, os registros se atualizam sem duplicar.
  • Persistência robusta: Suporte dual-mode a SQLite local e PostgreSQL via DATABASE_URL, com schema preparado para séries temporais.
  • Séries de evolução: Módulo app/services/historico.py gerando curvas de evolução patrimonial e crescimento acumulado.

📊 Fase 5: Analytics & Métricas Financeiras

Objetivo: Transformar dados brutos em inteligência de alocação e gestão de risco.

  • Rentabilidade temporal: Cálculo de retornos acumulados em janelas de 30 dias e YTD (Year-to-Date).
  • Alocação por classes: Consolidação percentual em Renda Fixa, Ações, FIIs e ETFs através de views e app/services/analytics.py.
  • Gestão de risco & concentração: Análise de exposição institucional (ex: % em Rico, Inter, Nubank) e diversificação de custódia.
  • Dashboard enriquecido: Páginas no Streamlit para visualização analítica (dashboard/pages/).

⏰ Fase 6: Automação & Sincronização Diária

Objetivo: Eliminar a necessidade de comandos manuais para alimentar o banco de dados.

  • Orquestrador agendado: Criação de app/core/scheduler.py utilizando APScheduler integrado ao ciclo de vida da aplicação.
  • Rotina operacional: Configuração do serviço systemd na máquina local/VM, executando a coleta automática sem depender de intervenção do usuário.
  • Alimentação contínua: Cada execução diária alimenta a base com dados reais do Open Finance (Pluggy), criando a matéria-prima para os gráficos da Fase 3 e os indicadores da Fase 5.
⚠️ Por que a Fase 7 foi crucial?
Com 28 arquivos de código-fonte em Python, regras financeiras estritas (cascata de valoração, cálculo de rentabilidade, deduplicação no banco) e integrações externas, qualquer pequena alteração poderia quebrar um cálculo silenciosamente. A Fase 7 estabelece as regras do jogo inegociáveis para que nenhum bug passe despercebido.

4. Qualidade Estática: Ruff e Mypy

⚡ Ruff (Linting + Formatação)

Substitui Flake8, Isort, Black e Pyupgrade com velocidade instantânea em Rust.

  • E, W, F: Erros sintáticos, imports não utilizados e estilo PEP 8.
  • I (Isort): Ordenação automática de imports com primeiro pacote app.
  • B (Bugbear): Prevenção de bugs sutis (ex: valores default mutáveis).
  • SIM (Simplify): Sugestões de simplificação de sintaxe Pythonica.
  • Regra B008 ignorada: Permite o padrão idiomático do FastAPI com Depends(...) como valor default de rotas.

🔍 Mypy (Verificação Estática de Tipos)

Checagem de consistência de tipos em tempo de desenvolvimento, sem precisar rodar o sistema.

  • Garante que argumentos e retornos obedeçam aos contratos declarados.
  • Elimina erros clássicos de AttributeError e TypeError: NoneType object has no attribute em produção.
  • Obriga clareza sobre quando uma variável pode ser nula (Optional[T] ou T | None).

🐛 O Bug Real que o Mypy Encontrou no pluggy_client.py

Muitas pessoas acham que tipagem estática é só "burocracia". No Open Wealth, o Mypy encontrou um bug lógico crítico no gerenciamento de tokens da Pluggy:

1. Incompatibilidade de tipos numéricos:

# Antes (erro no construtor e na expiração):
self._token_expiry = 0  # inferido como int
self._token_expiry = time.time() + self.TOKEN_LIFETIME  # time.time() retorna float!
# error: Incompatible types in assignment (expression has type "float", variable has type "int")

2. Bug de retorno silencioso de None:

# Antes (código que falharia silenciosamente quando o token ainda fosse válido):
def _get_token(self) -> str:
    if not self._token or time.time() > self._token_expiry:
        return self._authenticate()
    # Se o token AINDA ERA VÁLIDO, a função não tinha return e entregava None!
# error: Incompatible return value type (got "None", expected "str")

A Solução com Tipagem Estrita:

class PluggyClient:
    def __init__(self, ...):
        self._token: str | None = None
        self._token_expiry: float = 0.0

    def _get_token(self) -> str:
        if not self._token or time.time() > self._token_expiry:
            return self._authenticate()
        return self._token  # Agora sempre retorna str!

5. A Primeira Linha de Defesa: Git Pre-commit Hooks

Para evitar que código quebrado sequer chegue ao Git, configuramos o pre-commit. Ele roda automaticamente antes de cada git commit.

Arquivo .pre-commit-config.yaml

repos:
  - repo: https://github.com/astral-sh/ruff-pre-commit
    rev: v0.4.9
    hooks:
      - id: ruff
        args: [--fix]
      - id: ruff-format
  - repo: local
    hooks:
      - id: mypy
        name: mypy
        entry: ./.venv/bin/mypy app
        language: script
        types: [python]
        pass_filenames: false

Ao rodar git commit, se o código estiver desformatado, o hook formata os arquivos. Se o Mypy acusar tipo inválido, o commit é abortado imediatamente!

6. Entendendo a Fundo o GitHub Actions (CI/CD)

Você sempre subiu código para o repositório, mas como o GitHub Actions funciona por trás dos panos? E por que ele é tão valorizado na engenharia de software?

💡 O que é CI (Continuous Integration / Integração Contínua)?

É a prática de automatizar a integração e a validação de código de múltiplos desenvolvedores (ou de você mesmo ao longo do tempo). Em vez de esperar para descobrir problemas na hora de colocar o app em produção, o sistema valida cada alteração no instante exato em que ela é enviada ao repositório.

O Ciclo de Vida de um git push com CI

💻 1. Você executa no terminal local: git add . && git commit -m "feat: ..." && git push origin main
↓
🔔 2. O GitHub recebe o commit e ativa o Trigger: Identifica a regra configurada em .github/workflows/ci.yml (on: push: branches: [main])
↓
☁️ 3. O GitHub provisiona uma Máquina Virtual Limpa: Um servidor Ubuntu 24/22 zerado na nuvem (Runner), sem nenhum arquivo ou pacote prévio
↓
⚙️ 4. Execução sequencial dos passos do Workflow: Checkout do código → Setup do Python → Instalação de dependências → Lint → Type Check → Testes
↓
🟢 5. O Veredito Final: Se todos os passos retornarem exit code 0 → Badge Verde. Se qualquer passo falhar → Pipeline Vermelho

O Paradoxo do "Na Minha Máquina Funciona!"

No seu computador local, você já possui um ambiente virtual configurado há semanas: pacotes instalados em tempos diferentes, dependências que você instalou manualmente com pip install e esqueceu de anotar, arquivos temporários ignorados no .gitignore, etc.

O GitHub Actions é a prova de fogo: Ele roda em um ambiente totalmente estéril. Se o projeto passou no runner do GitHub, significa que qualquer pessoa no mundo ou qualquer servidor de produção conseguirá baixar o código e executá-lo sem problemas.

7. Estudo de Caso Real: Por que o Actions falhou na 1ª tentativa e como resolvemos

Durante a implementação da Fase 7, passamos exatamente pela situação clássica que todo time de tecnologia enfrenta:

1
Sintoma: No terminal local, mypy app passava sem nenhum erro (0 erros em 28 arquivos). Porém, ao subir para o GitHub, o job pipeline ficou vermelho.
2
Diagnóstico no log do GitHub Actions: O passo Lint with Ruff passou com louvor. Mas no passo Type check with Mypy, surgiram dezenas de erros: 
app/core/config.py:3: error: Cannot find implementation or library stub for module named "pydantic_settings"
app/core/database.py:4: error: Cannot find implementation or library stub for module named "psycopg"
app/core/database.py:5: error: Cannot find implementation or library stub for module named "psycopg.rows"
3
Causa Raiz Descoberta: O workflow rodava pip install .[dev] (que lia apenas o pyproject.toml). No entanto, pacotes vitais do projeto como pydantic-settings e psycopg estavam declarados no requirements.txt! Na VM zerada do GitHub, eles simplesmente não haviam sido instalados.
4
Correção Aplicada: Adicionamos a instalação explícita do requirements.txt na etapa de setup do workflow. 
- name: Install dependencies
  run: |
    python -m pip install --upgrade pip
    pip install -r requirements.txt
    pip install .[dev]
5
Resultado da Execução #3: Sucesso total em 42 segundos. O pipeline executou Lint, Mypy em 28 arquivos, 176 testes unitários/integração com 100% de cobertura e build do pacote Python!

8. O Arquivo Final do Pipeline: .github/workflows/ci.yml

Abaixo está a configuração completa e comentada que governa a esteira de integração contínua do Open Wealth: 

name: CI

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  pipeline:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Set up Python 3.11
        uses: actions/setup-python@v5
        with:
          python-version: "3.11"
          cache: "pip"

      - name: Install dependencies
        run: |
          python -m pip install --upgrade pip
          pip install -r requirements.txt
          pip install .[dev]

      - name: Lint with Ruff
        run: |
          ruff check .
          ruff format --check .

      - name: Type check with Mypy
        run: |
          mypy app

      - name: Run tests with Coverage
        run: |
          pytest --cov=app --cov-report=term-missing

      - name: Build package check
        run: |
          pip install build
          python -m build
