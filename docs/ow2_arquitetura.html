Open Wealth — Tutorial da Fase 2

API (FastAPI) + persistência de snapshots · idempotência validada · SQLite em produção de dados

1. O que a Fase 2 entrega

Na Fase 1, o app sabia calcular um snapshot mas o esquecia. A Fase 2 fecha o ciclo: o snapshot passa a ser gravado em disco e exposto por uma API HTTP, criando a base de dados histórica que o dashboard de evolução precisa.

Três entregas:

  1. Persistência — SnapshotRepository grava posições sem duplicar snapshots do mesmo dia (idempotência validada).
  2. API — POST /api/v1/sync dispara o ciclo Pluggy → posições → banco (202 Accepted).
  3. Observabilidade — log estruturado em JSON com eventos nomeados por etapa do sync.

2. O fluxo completo do sync

POST /api/v1/sync FastAPI recebe a chamada (curl, scheduler ou dashboard)
sync_weekly(client, repo) Orquestra: busca na Pluggy, monta posições
SnapshotRepository Verifica se já existe snapshot do dia → grava ou pula
202 Accepted Evento snapshot_saved ou snapshot_skipped

Detalhe de desenho: o serviço recebe o cliente e o repositório como parâmetros — sem singletons nem estado global. O endpoint apenas monta as dependências e delega.

3. Schema autoconstruído — o fim do "tabela não existe"

O repositório chama _ensure_schema() no próprio __init__. Em banco novo, as tabelas já existem antes da primeira operação — a classe de bugs "no such table" em ambiente limpo desaparece.

  1. DDL idempotente: CREATE TABLE IF NOT EXISTS — rodar quantas vezes quiser não altera nada.
  2. Migração incremental: _migrate_schema() separada, para evoluções de colunas sem resetar o banco.
  3. Custo consciente: construir schema na instanciação muda o contrato — mocks de teste precisam estar cientes de que o construtor tocará no banco.

4. Idempotência — um snapshot por dia

A regra central da fase: rodar o sync duas vezes no mesmo dia não duplica dados. A checagem vive no repositório, não no serviço:

upsert_snapshot(snapshot, data) →

  1. snapshot_exists(data) — SELECT por data;
  2. se existe → pula, loga snapshot_skipped, nem chega a chamar a API;
  3. senão → insere posições (asset_name, category, amount) + metadados de contas, commit() explícito.
💡 Por que no repositório e não no serviço? A dedup por data é uma regra dos dados, não da orquestração. Assim qualquer chamador (endpoint, scheduler, teste) herda a garantia de graça.

5. Verificação ponta a ponta (sandbox)

Prova de que a idempotência funciona no mundo real, não só nos mocks:

$ curl -X POST http://localhost:8000/api/v1/sync
# 1ª chamada → 202, log: sync_started → sync_data_fetched → snapshot_saved
# 2ª chamada → 202, log: sync_started → snapshot_skipped  ✅

$ sqlite3 data/database.db "SELECT asset_name, category, amount FROM snapshots;"
Conta Corrente   | banco  |   43701.43
Mastercard Black | cartao |   -1006.20

Soma confere: 43701.43 − 1006.20 = 32695.23. (O 42695.23 de uma checagem anterior era resíduo do banco antigo antes do rm -f — a diferença de R$ 10.000 era fantasma, não bug.)

⚠️ Armadilha registrada: apagar data/database.db com o uvicorn --reload rodando "funciona" (SQLite recria na próxima conexão), mas o processo antigo pode segurar conexões abertas. Preferir reiniciar o server após rm.

6. Log estruturado — eventos, não frases

Cada etapa do sync emite um evento JSON nomeado. Em vez de "salvando dados..." em texto livre, o sistema fala em vocabulário fixo:

Evento Significado Ação ao diagnosticar
sync_started POST chegou — (normal)
sync_data_fetched Pluggy respondeu Ausência aqui = problema no cliente HTTP
snapshot_saved Gravação concluída — (normal)
snapshot_skipped Já existia snapshot do dia — (esperado no 2º sync)

Exemplo de linha real:

{"event": "snapshot_saved", "nivel": "INFO", "data": "2025-11-14",
 "assets": 24, "timestamp": "2025-11-14T10:22:03"}

7. O endpoint sob a lupa

POST /api/v1/sync é deliberadamente minúsculo — nenhuma regra de negócio dentro dele: 

@app.post("/api/v1/sync", status_code=202)
def trigger_sync():
    logger.info("sync_started", extra={"event": "sync_started"})
    client = PluggyClient(...)
    repo = SnapshotRepository()
    sync_weekly(client, repo)
    return {"status": "accepted"}

Decisões de desenho:

  1. 202 Accepted: o sync não é instantâneo nem síncrono no sentido estrito — 202 comunica "recebido, em processamento".
  2. Sem lógica no endpoint: ele só monta dependências e delega. Isso mantém sync_weekly testável sem HTTP.
  3. Erros propagam: falha da Pluggy → exceção → FastAPI devolve 500 com log estruturado; o cliente não recebe "sucesso" enganoso.

9. Lições de processo (do CONTEXT.md)

  • Introspecção > adivinhação: antes de escrever, verificar Position.__dataclass_fields__ — asset_name, não name. Um erro de coluna aqui quebraria o INSERT silenciosamente.
  • Soma confere: após o E2E, validar aritmeticamente o resultado (43701.43 − 1006.20 = 32695.23) — não apenas "tem linhas na tabela".
  • Reiniciar o server após rm do banco: o --reload do uvicorn esconde o problema de conexões abertas.
  • Verificar o log antes de olhar a tabela: os eventos dizem onde o fluxo parou; a tabela só diz o que ficou.

10. O que a Fase 3 herda

  • Histórico real: o banco já tem snapshots datados — o get_between(inicio, fim) já testado alimenta os gráficos.
  • Endpoints de leitura: o próximo GET /api/v1/snapshots reutiliza o repositório sem alteração.
  • Segurança: credenciais da Pluggy agora em variáveis de ambiente (não mais hardcoded no endpoint).
  • Robustez: retry com backoff na Pluggy e o endpoint assíncrono, para não travar o worker.

11. Resumo em uma frase

O POST /api/v1/sync delega ao sync_weekly, que busca na Pluggy e grava via SnapshotRepository com schema autoconstruído e dedup por dia — e os 17 testes + os eventos de log garantem que o histórico seja confiável, não apenas presente.
