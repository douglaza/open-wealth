💰 Open Wealth — Fase 1

Como o sistema conecta ao Pluggy, consolida seu patrimônio em um snapshot diário e garante isso com 17 testes.

1. Visão geral da arquitetura

A Fase 1 responde a uma pergunta: “quanto eu tenho, onde eu tenho, hoje?”. O fluxo completo tem 4 etapas:

🔌 PluggyClient Busca dados na API do Pluggy (contas + investimentos)
↓
🔄 sync_all(client) Transforma a resposta bruta da API em um Snapshot
↓
💾 SnapshotRepository Persiste o snapshot do dia (sem duplicar se rodar 2x)
↓
📊 get_totals(snapshot) / rentabilidade Agrega por instituição e calcula retornos para o dashboard

2. O cliente Pluggy

PluggyClient é a única porta de entrada de dados externos. Toda requisição envia o token no header X-API-KEY e, em caso de erro HTTP, levanta uma exceção própria — nada de silenciar falhas.

Os 4 métodos que importam

MétodoO que retorna
get_item()Metadados da conexão — inclui o nome da instituição (ex.: “Itaú”, “BTG”)
get_accounts()Contas (corrente, cartão...) com balance
get_investments()Investimentos (CDB, ETF...) — os campos variam por produto ⚠️
get_transactions()Transações para cálculo de rentabilidade
⚠️ Ponto crítico descoberto na Fase 1: a API de investimentos retorna campos inconsistentes por produto — value: null com balance preenchido, ou amount divergente de balance. Isso motivou a cascata da seção 3.

3. sync_all — o coração da consolidação

sync_all(client) orquestra tudo e produz um Snapshot: uma foto do patrimônio na data de hoje, como lista de Position.

3.1 Modelo Position (dataclass)

@dataclass
class Position:
    institution: str   # ex.: "BANCO BTG PACTUAL S/A"
    account_type: str # CHECKING | CREDIT | FIXED_INCOME | ETF...
    asset_name: str   # ⚠️ nome do ativo é asset_name, NÃO "name"
    category: str
    amount: float     # valor resolvido pela cascata (seção 3.2)
    updated_at: date

3.2 A cascata de valores (contrato 4.8/4.9)

Qual é o valor real de um investimento? O contrato define uma ordem rígida de prioridade — e o amount da API nunca é usado:

1ª balance Fonte da verdade — é o que o dashboard do banco exibe
↕ se balance ausente/nullfallback
2ª value Fallback para produtos que não reportam balance
↕ se value também ausente/nullfallback
3ª 0.0 Melhor zerar do que inventar um valor
🚫 Por que amount é banido? Caso real (sandbox BTG): o CDR reportava amount=2500 mas balance=2000 — o dashboard do banco exibia 2000. Usar amount inflaria o patrimônio em R$ 500 fantasma.

4. SnapshotRepository — persistindo sem duplicar

Repositório que grava o snapshot no banco. Duas regras de negócio importantes (ambas testadas):

  1. Um snapshot por dia: se sync_all rodar duas vezes no mesmo dia, o segundo save atualiza em vez de duplicar (teste: save_same_day_twice_does_not_duplicate).
  2. Consulta por período: get_between(inicio, fim) filtra por data — base para os gráficos de evolução do patrimônio (teste: get_between_filters_by_period).

5. get_totals — agregação pós-cascata

get_totals(snapshot) soma as posições por instituição. O detalhe sutil: a soma usa os valores após a cascata, nunca os valores brutos da API.

Exemplo do teste de agregação

Mesma instituição (BTG), dois produtos com fontes de verdade diferentes:

Ativobalancevalueamount Valor usado
CDB2000null 25002000

Total BTG = 2150.0 ✅ Soma correta dos valores resolvidos. Se usasse amount bruto → 2650 ❌. Se zerasse posições com value=null → 150 ❌.

6. Scheduler — a rotina semanal

Um agendador dispara sync_all periodicamente, garantindo que o snapshot stay atualizado sem intervenção manual (teste: test_sync_weekly_runs).

7. A suíte de testes — 17 passed

Organização dos testes e o que cada grupo protege:

🧪 Metodologia aplicada: os testes de regressão foram escritos antes de verificar o código. Como passaram de primeira, eles confirmaram o contrato em vez de "corrigir às cegas" — e agora travam a porta: se alguém reordenar a cascata, o CI acusa.

8. Lições de processo (do CONTEXT.md)

  1. Colar com verificação: sempre cat arquivo após colar um bloco — pegou conteúdo ausente na primeira tentativa.
  2. Introspecção > adivinhação: um comando (Position.__dataclass_fields__) revelou que o campo é asset_name, economizando tentativa e erro.
  3. Teste antes de olhar o código: descreve o contrato, não a implementação.

9. Resumo em uma frase

O PluggyClient busca, o sync_all resolve cada posição pela cascata balance → value → 0.0, o SnapshotRepository guarda sem duplicar, e 17 testes garantem que nada disso quebre silenciosamente.
